# 日终决策邮件：调试数值 + 特征/行情 CSV 附件 —— 设计与修改方案

> 来源需求（`service/doc/优化.md`）：
> 「日终策略决策时，希望邮件能给出调试分析的数值信息，例如概率，运算结果等等，最好附一份 CSV 特征文件以及信号生成时以来的数据内容，以便事后分析」
>
> 本文只做设计，未改动任何生产代码。

### 1.2 决策时刻可用数值（关键：都已在内存里）

`StartDaily` 在 replay 结束后调用 `SendSummaryEmail`（实盘 `AgentSubSystem.cpp:1788`、回测 `:1596`），此时该次运行的 `DataContext` 仍然存活，并且：

- 所有节点输出都以**时间序列**形式保存在 `DataContext::_outputs`（`unordered_map<String, context_t>`，DataContext.h:366），key = `{symbol}.{label}`，每个 epoch 追加一个值，`vec.back()` 即决策 bar 取值；
- 时间轴 `context.GetTime()`（DataContext.h:247）与上述序列一一对齐；
- 已有整体导出 API `DataContext::CollectNumericOutputs(Map<String, Vector<double>>&)`（DataContext.h:343，实现 DataContext.cpp:26）；
- 图结构 `flow._graph: List<QNode*>` 提供 key → 节点类型/标签的映射：`node->out_elements()`（StrategyNode.h:95）。

**结论：不需要改任何节点、不需要二次 replay，就能拿到决策 bar 的全部数值。**

以生产策略 CTA_v16 为例（`service/build/scripts/CTA_v16`，42 只行情标的，信号池 4 只）：

| 类别 | context key | 说明 |
|---|---|---|
| 模型概率 | `{sym}.xgb_probs_0/1/2` | `multi:softprob`，3 分类，15 特征 |
| 模型标签 | `{sym}.xgb_prediction` | argmax 类别 |
| 派生运算 | `{sym}.raw_strength`、`.filtered_strength`、`.strength_med_20d` | FormulaNode，raw_strength = 符号×最大概率×(1−归一化熵) |
| 特征值 | `{sym}.norm_ret/.r2/.trend_str/.vpcorr/.slope_z/...`、`{sym}.emd.nimf_0..4`、`{sym}.emd.volume_regime`、`{sym}.pvs_ma_z` | 模型 15 特征的来源 |
| 信号/执行 | `{sym}.signal`(1/0/−1)、`{sym}.plan_action/.plan_qty/.plan_price` | SignalNode.cpp:184、PortfolioNode.cpp:227 |
| 原始行情 | `{sym}.close/open/high/low/volume` 与 `{sym}.org_*`（不复权） | QuoteNode.cpp:41-64 |

### 1.3 缺口：截面函数中间量不在 context 里

CTA_v16 的买入条件为：

```
(max(cs_count(raw_strength, 1), cs_count(raw_strength, -1)) / cs_size()) >= 0.6 and topk(raw_strength, 3)
```

`cs_count / cs_size / topk` 的取值只存在于 `FormulaParser` 的 `CrossSectionGraph::nodes[].outputs`（Stmt.h:47-64），求值结束即丢弃，**不会**写回 context。也就是说：

- 「今天为什么没买」这个最核心的问题（cs 比值 = 0.583 < 0.6？topk 没进前 3？），光靠 context 里的 key 答不出来；
- 但 `FormulaParser::computeNumeric(symbols, args, context)`（Stmt.h:122，实现 FormulaParserEval.cpp:602）是 public 的，内部自带 `buildCrossSectionGraph + computeCrossSectionGraph`，因此**可以在报告构建阶段对同一份冻结 context 重新求值任意表达式，结果与决策时同口径**。SignalNode 使用 `_pools` 作为截面样本（`envoke(_pools, ...)`，SignalNode.cpp:115），所以必须用 `SignalNode::GetPool()`（已存在，SignalNode.h:27）的同一 universe，否则 `cs_size()` 分母不同、结果不可比。

## 2. 设计目标

1. **可自证**：收到邮件的人不看日志、不登机器，就能判断"今天为什么买/卖/不买"。
2. **零热路径成本**：全部采集发生在 replay 结束、决策 bar 之后，不动任何 `Process()`。
3. **零维护**：默认从图自动发现要展示的数值；配置只用于裁剪体积和补充语义（如类别名）。
4. **失败不影响决策**：报告/附件生成、邮件发送的任何异常都不得影响决策落库与后续流程；单项求值失败只降级该列。
5. **可对拍**：CSV 与 Python 训练/回测脚本的输入严格对齐（列序、17 位精度），沿用现有宽表格式。

## 3. 输出分三层

| 层 | 载体 | 内容 | 体积 |
|---|---|---|---|
| A | 邮件正文新增区块「决策解释」 | 每个决策标的：概率、raw_strength 链、截面比值、子条件真假、目标数量；HOLD 取 TopN | 几 KB |
| B | 附件 `snapshot_<date>.csv` | **决策 bar 截面**：一行一标的，列 = 模型特征（按模型顺序）+ 概率 + 派生值 + plan + 最终条件 | 1~20 KB |
| C | 附件 `series_<date>.csv` | **信号生成以来（滚动窗口）时间序列**：宽表，`datetime` + `{sym}.{col}`，默认 60 根 × 决策标的，含 OHLCV/org_*/概率/派生值/signal | 数十~数百 KB |
| D | 落盘（可选附件） | 策略已有 `DebugNode` 的全量 dump（如 `xgb_debug.csv`，251 行 × 925 列 = 729 KB） | < 2 MB |

D 是"全量原始数据"，B/C 是"当期可读结论"。**已确定**：A + B + C 走邮件，D 只落盘并通过配置开关决定是否外发。

附件范围（已确定）：

- **snapshot.csv**：决策 bar 截面，一行一标的（**仅决策标的**，即 BUY/SELL + HOLD TopN），列 = 模型特征（按模型输入序）+ 概率 + 派生值 + plan + 最终条件。体积 1~20 KB，必附。
- **series.csv**：信号生成以来的滚动窗口时间序列，宽表，`datetime` + `{sym}.{col}`。**默认 60 根 × 仅决策标的**（非全 universe），含 OHLCV/org_*/概率/派生值/signal。体积数十~数百 KB，必附。
- 决策标的 = `manualTiming->getDecisions()` 中 BUY/SELL 的 symbol 集合 + HOLD 按 `|filtered_strength|` 取 TopN（默认 5，可配）。
- 全量 DebugNode dump（D 层）默认不附，仅落盘；需要时通过 `attachFullDump = true` 显式开启。

目录约定（与 DebugNode 的 `{dbPath}/debug/{strategy}/` 并列，避免互相覆盖）：

```
{dbPath}/reports/{strategy}/{date}/snapshot.csv
{dbPath}/reports/{strategy}/{date}/snapshot.schema.json   # 列名 → context key / 节点标签 / 类型
{dbPath}/reports/{strategy}/{date}/series.csv
{dbPath}/reports/{strategy}/{date}/body.html             # 邮件正文快照，便于事后核对与测试断言
```

> `body.html` 落盘很重要：邮件正文只存在于收件箱里，出了问题无法回溯；同时让集成测试可以只跑图、断言 HTML 内容，而不必真的发信。

## 4. 邮件正文新增区块（示意）

```
┌ 决策解释 ─────────────────────────────── 窗口 60 根 · 模型 CTA_v16-CTA_v16.json ─┐
│ 标的        决策   P0     P1     P2    raw_str  med20  filt   cs比  topk  str>med  买入 │
│ sz.000423   BUY    0.11   0.24   0.65   0.412   0.207  0.205  0.75   ✓    ✓        ✓  │
│ sz.002825   HOLD   0.31   0.28   0.41   0.107   0.190  0.000  0.75   ✓    ✗(0.107≤0.190)  ✗  │
│ sz.003007   SELL   0.55   0.21   0.24  -0.180   0.150  0.000  0.75   ✗    —        ✓  │
│ sz.301110   HOLD   0.28   0.35   0.37   0.052   0.165  0.000  0.75   ✗    ✗(0.052≤0.165)  ✗  │
│ ...（HOLD 按 |filtered_strength| 取 Top5）                                              │
├ 生成文件 ─────────────────────────────────────────────────────────────────────────────┤
│ snapshot_2026-09-22.csv (3.1 KB) · series_2026-09-22.csv (86 KB)                      │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

**解释粒度说明**（对应 §4.5）：

- `cs比` = `max(cs_count(raw_strength,1), cs_count(raw_strength,-1)) / cs_size()`，标量结果；
- `topk` = 该标的是否在 `topk(raw_strength, 3)` 中，✓/✗；
- `str>med` = `raw_strength > strength_med_20d`，标量比较，✗ 时显示实际值与阈值；
- `买入` 列 = 最终买入条件（`cs比 >= 0.6 and topk and str>med`），✗ 时显示失败原因。

要点：

- 「买入条件/卖出条件」列展示 `✓` 或 `✗(实际值 关系 阈值)`，这是回答"为什么没信号"的关键一列；
- 类别名（P跌/P平/P涨）**不要猜**：模型只给 `xgb_probs_0..2`，语义由训练侧决定。默认显示 `P0/P1/P2`，可在配置里给 `classNames` 覆盖（CTA_v16 的 `raw_strength` 用 `probs[0]` vs `probs[2]` 判方向，可推 0=跌、2=涨，但不应硬编码到通用代码里）；
- 正文只放决策标的 + `holdTopN`，其余全部进 CSV；
- 无信号日（全 HOLD）**同样发送**——这种日子恰恰最需要数值来区分"确实没信号"和"特征坏了/预热不足"。

## 4.5 解释粒度设计（已确定：标量结果 + 子条件分解）

**已确定**：采用**标量结果 + 子条件分解**方案（P0/P1），不做 AST 级 trace（P2）。理由：

1. **标量够用**：CTA_v16 的买入条件 `(max(cs_count(raw_strength,1), cs_count(raw_strength,-1)) / cs_size()) >= 0.6 and topk(raw_strength,3)` 可以分解为 3 个标量：
   - `cs_count_pos = cs_count(raw_strength, 1)`（正 strength 标的数）
   - `cs_count_neg = cs_count(raw_strength, -1)`（负 strength 标的数）
   - `cs_ratio = max(cs_count_pos, cs_count_neg) / cs_size()`（截面比值）
   - `in_topk = topk(raw_strength, 3)`（是否在前 3）
   
   这 4 个标量足以回答"为什么没买"：`cs_ratio = 0.583 < 0.6` 或 `in_topk = false`。

2. **AST trace 成本高**：需要给 `FormulaParser` 加非热路径 trace 模式（记录每个 identifier/函数调用的取值与比较结果），实现复杂且只在调试时有用；标量方案只需对 `spec.explain` 里的表达式求值，零侵入。

3. **可扩展**：如果标量不够，后续可以在 `spec.explain` 里加更多表达式（如 `raw_strength > strength_med_20d`），不需要改代码。

### 4.5.1 解释结构

每个决策标的的解释包含：

```json
{
  "symbol": "sz.002825",
  "decision": "HOLD",
  "probabilities": { "P0": 0.31, "P1": 0.28, "P2": 0.41 },
  "derived": {
    "raw_strength": 0.107,
    "strength_med_20d": 0.190,
    "filtered_strength": 0.000
  },
  "conditions": {
    "cs_ratio": { "value": 0.75, "threshold": 0.6, "pass": true },
    "in_topk": { "value": true, "pass": true },
    "raw_strength > med": { "value": 0.107, "threshold": 0.190, "pass": false }
  },
  "final": {
    "buy_condition": { "pass": false, "reason": "raw_strength(0.107) <= med(0.190)" },
    "sell_condition": { "pass": true, "reason": "not topk(raw_strength, 3)" }
  }
}
```

### 4.5.2 求值流程

1. **取 universe**：`SignalNode::GetPool()`（CTA_v16 是 4 只标的），用于 `cs_size()` 分母。
2. **取冻结 context**：`DataContext` 在决策 bar 上的快照（所有节点输出已累积）。
3. **对 `spec.explain` 每条表达式求值**：
   - 用 `FormulaParser::computeNumeric(universe, args, context)`，内部自动构建截面图并求值。
   - `args` = 该策略所有上游 `out_elements()` 的 key 集合（与 SignalNode 同款）。
   - 单条失败只记 warning，不中断其他表达式。
4. **分解子条件**：
   - 如果表达式是 `A >= B`，记录 `A.value`、`B.value`、`pass = (A >= B)`。
   - 如果表达式是 `topk(expr, k)`，记录 `pass = (symbol in top-k)`。
   - 如果表达式是 `cs_count(expr, sign)`，记录 `value = count`。
   - 复合条件（`and/or`）递归分解，最终 `final.buy_condition` 是所有子条件的 `and`。
5. **生成 HTML 片段**：
   - 每个决策标的一行，列 = 概率 + 派生值 + 子条件（✓/✗ + 实际值）+ 最终条件（✓/✗ + 原因）。
   - HOLD 标的按 `|filtered_strength|` 取 TopN（默认 5）。

### 4.5.3 配置示例

```json
"debug": {
  "explain": [
    "raw_strength",
    "strength_med_20d",
    "filtered_strength",
    "cs_count(raw_strength, 1)",
    "cs_count(raw_strength, -1)",
    "cs_size()",
    "max(cs_count(raw_strength,1), cs_count(raw_strength,-1)) / cs_size()",
    "topk(raw_strength, 3)",
    "raw_strength > strength_med_20d"
  ]
}
```

**自动推导**：如果 `explain` 为空，自动从 `SignalNode` 的 `buy/sell` 表达式提取所有 identifier 和函数调用，生成等价解释列表（需要解析 AST，但只做一次，不重）。

### 4.5.4 降级策略

- 表达式求值失败：该列显示 `—`，warning 记入 `EodDebugReport::warnings`。
- 缺失 key：列显示 `NaN`，warning 说明。
- 无信号日：所有 HOLD 标的的解释仍然计算（区分"确实没信号"和"特征坏了"）。

### 5.3 新增 `service/include/Util/EodReport.h` + `service/src/Util/EodReport.cpp`

核心模块，唯一负责"把决策时刻的数值变成正文片段 + CSV + 附件清单"：

```cpp

    int  maxSnapshotColumns = 40;     // snapshot 列数上限，避免 925 列全量

struct EodDebugReport {
    nlohmann::json rows;              // 结构化数值（同时写入 decisions/{date}.json）
    String htmlSection;               // 邮件正文片段
    Vector<String> attachments;       // 实际落盘、可外发的文件
    String summaryLine;               // "snapshot.csv (3.1 KB) · series.csv (86 KB)"
    Vector<String> warnings;          // 降级说明（缺失列、超限丢弃等）
};

EodDebugReport BuildEodDebugReport(Server* server, const String& strategy,
                                   const List<QNode*>& graph,      // flow._graph
                                   const DataContext& context,     // 冻结在决策 bar
                                   const Set<symbol_t>& universe,  // SignalNode::GetPool()
                                   const Map<symbol_t, DecisionSnapshot>& decisions,
                                   const EodDebugSpec& spec);
```

内部步骤（全部在 replay 结束后、决策 bar 上）：

1. **取标签映射**：遍历 `graph`，`node->out_elements()` → `key → {nodeType, label, field}`；识别 `xgb_probs_*` / `onnx_*` / `signal` / `plan_*` / HMM 等无 symbol 前缀的全局 key。
2. **取数**：按需 `context.get<Vector<double>>(key).back()`；仅在需要全量时才调 `CollectNumericOutputs`（925 列 × 251 行 ≈ 1.8 MB，能省则省）。
3. **模型特征列序**：从 `XGBoostNode`/`OnnxInferenceNode` 取"推理实际使用的顺序"（新增 getter，见 5.6），保证 snapshot.csv 的列序 = 模型输入序。
4. **explain 求值 + 子条件分解**（见 §4.5）：
   - 对 `spec.explain` 每条表达式 new 一个 `FormulaParser`，`parse` 后用 `computeNumeric(universe, args, context)` 求值；`args` 取该策略所有上游 `out_elements()` 的 key 集合（与 SignalNode 同款做法）。
   - 自动分解子条件：`A >= B` → 记录 `A.value`/`B.value`/`pass`；`topk(expr, k)` → 记录 `pass = (symbol in top-k)`；`cs_count(expr, sign)` → 记录 `value = count`；复合条件（`and/or`）递归分解。
   - 最终 `买入/卖出` 列 = 所有子条件的 `and`，✗ 时显示失败原因（如 `"raw_strength(0.107) <= med(0.190)"`）。
   - 单条失败只记 warning，不中断其他表达式。
5. **写 CSV**：调用 5.5 的公共 writer。

## 6. 配置项

策略 JSON 顶层（与 `capital`/`backtest` 平级）：

```json
"debug": {
  "email": true,
  "subject": "[QuasarX] {strategy} 日终决策 {date} · BUY{buy}/SELL{sell}",
  "classNames": ["跌", "平", "涨"],
  "explain": [
    "raw_strength",
    "strength_med_20d",
    "filtered_strength",
    "max(cs_count(raw_strength,1), cs_count(raw_strength,-1)) / cs_size()",
    "topk(raw_strength,3)"
  ],
  "series":   { "bars": 60, "attach": true, "columns": "auto" },
  "snapshot": { "attach": true },
  "holdTopN": 5,
  "maxAttachMB": 20
}
```

缺省行为（不配任何东西）：自动推导列 = 模型特征（按模型顺序）+ 概率 + 派生 formula 输出 + `signal` + `plan_*` + OHLCV；`bars = min(60, 窗口长度)`；B/C 都附；`holdTopN=5`。

全局兜底放 `config.json` 的 `server.notice.report`（`enabled` / `bars` / `maxAttachMB`），用于一次性关闭或统一限流；策略级优先。

## 7. 风险与取舍

| 风险 | 说明 | 处置 |
|---|---|---|
| 邮件体积 / 进入垃圾箱 | HTML 正文过大、附件 base64 膨胀 33%；QQ 单封上限约 50 MB | 正文只放决策标的 + holdTopN；序列默认 60 根 × 决策标的；超 `maxAttachMB` 只落盘不外发并在正文提示路径 |
| 发送失败被静默 | `mail.py` 现在吞异常退 0，`RunCommand` 误报成功 | 随本次一并修（§5.1）；C++ 侧发送结果打日志 |
| 附件含完整特征与价格 | 数据外泄面扩大 | 仍是配置里的单一收件人；如需多人，把 receiver 支持逗号分隔（`sendmail(sender, [r1, r2], ...)`） |
| explain 重跑截面计算 | 42 标的 × 少量表达式 | 毫秒级且不在热路径；每条表达式独立 try/catch，失败降级为缺列 |
| 概率语义误读 | 类索引 → 涨/跌/平 是训练侧约定，代码无法推断 | 默认展示 `P0/P1/P2`，语义靠 `classNames` 配置显式声明，不硬编码 |
| 列数膨胀 | CTA_v16 全量 925 列，多策略并存时更大 | snapshot 列数上限 + 按需取 key，避免 `CollectNumericOutputs` 全量拷贝 |
| 与现有 DebugNode 重复 | 两处都在写 CSV | 抽取公共 `WriteWideCsv`（§5.5）；EodReport 负责"当期报告"，DebugNode 保持"全量 dump" |
| 时机 | DebugNode dump 晚于发信 | EodReport 自产 CSV，不依赖节点 dump（§5.4） |
